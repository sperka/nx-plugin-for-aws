The `ts#greengrass-component` generator adds an [AWS IoT Greengrass v2](https://docs.aws.amazon.com/greengrass/v2/developerguide/what-is-iot-greengrass.html) component to an existing TypeScript project: a recipe, a sample entrypoint, and the Nx targets to bundle the component and deploy it locally to a core device.

With the default `infra: component-version` (unless `--infra none`), it also vends a `GreengrassComponentVersion` CDK construct (or Terraform module) that publishes the component's built artifact to AWS IoT Greengrass - pair it with a <Link path="guides/greengrass-deployment">`greengrass-deployment`</Link> project's artifact bucket to actually deploy it to a thing or thing group.

## Generator Output

The generator adds the following files to your project:

<FileTree>

- greengrass
  - \<component-name>
    - recipe.yaml the component recipe — user-owned from first generation onward
- src
  - greengrass
    - \<component-name>
      - main.ts the component entrypoint — user-owned from first generation onward

</FileTree>

With `--gdkConfig`, the generator also vends `gdk-config.json`, a GDK-shaped build config for running the GDK CLI by hand.

Unlike `py#greengrass-component`, the entrypoint lives under your project's own `src/` tree (not beside `recipe.yaml`), so it compiles, lints and type-checks as part of the project's normal TypeScript targets.

## The Bundle and Its Targets

TypeScript source is never packaged directly - the deployable content is a single-file bundle. The generator wires a shared `bundle` target (via the same [`rolldown`](https://rolldown.rs/) bundling this repo uses for `ts#lambda-function` and `ts#mcp-server`) plus targets prefixed with the component's kebab-case name (`<c>` below):

| Target             | Purpose                                                                          | Cached | Depends on |
| ------------------ | --------------------------------------------------------------------------------- | ------ | ---------- |
| `bundle`           | Bundles every entrypoint in the project (Lambda functions, MCP servers, this component, ...) into single-file, `node`-platform output | Yes    | `compile`  |
| `<c>-vendor`       | ipc: true only - copies this build's aws-crt addon next to the bundle output      | Yes    | `bundle`   |
| `<c>-artifact`     | Zips the component's bundle output (staged output, when ipc: true) into a GDK-shaped layout | Yes    | `<c>-vendor` when ipc: true, else `bundle` |
| `<c>-deploy-local` | Creates a local deployment via `greengrass-cli`, then verifies the component started — runs **on** the core device | No     | `<c>-artifact` |
| `<c>-logs`         | Tails the component's log file — runs **on** the core device                      | No     | -          |

`<c>-artifact` is also wired onto the project's `build` and `assemble` targets, so a normal build always produces a fresh artifact.

`bundle` is shared with any other bundled entrypoint in the same project (a Lambda function added with `ts#lambda-function`, for example) - each entrypoint gets its own `rolldown.config.ts` entry and its own output subdirectory, but running `bundle` rebuilds all of them together. A dedicated project per component (the same production default `py#greengrass-component` recommends) keeps device-oriented bundling (a fixed `node` floor and a vendored native addon) from sharing a cache-invalidation boundary with unrelated cloud-oriented bundles (a Lambda function's, with `@aws-sdk/*` external).

This uses [`rolldown`](https://rolldown.rs/) to produce a single-file, `node`-platform bundle at:

- dist/\<project-root>/bundle/greengrass/\<component-name>
  - index.js the bundled entrypoint

</FileTree>

<OptionFilter when={{ ipc: true }} description="ipc=true bundles aws-iot-device-sdk-v2 like everything else">

With `ipc: true`, `aws-iot-device-sdk-v2` is bundled like everything else. The one thing a bundler cannot inline is [`aws-crt`](https://github.com/awslabs/aws-crt-nodejs)'s native addon - the `<c>-vendor` target copies it into the artifact instead. </OptionFilter>

<OptionFilter when={{ ipc: false }} description="ipc=false bundles everything, with no external dependency">

With `ipc: false` (the default), nothing is marked external: the bundle is fully self-contained and needs nothing installed on the device beyond a `node` binary.

</OptionFilter>

### Building the artifact (`<c>-artifact`)

<NxCommands commands={['run <project>:<component-name>-artifact']} />

This zips the bundle output - plus, when `ipc: true`, the vendored addon `<c>-vendor` staged next to it - into a zip at the archive root - not the TypeScript source that produced it - and writes the resolved recipe alongside it:

<FileTree>

- dist/\<project-root>/greengrass/\<component-name>
  - greengrass-build
    - recipes
      - \<ComponentName>-\<version>.yaml resolved recipe
    - artifacts
      - \<ComponentName>
        - \<version>
          - \<component-name>.zip the deployable artifact

</FileTree>

This layout is **GDK-shaped, not GDK-compatible**: it matches the directory structure the [Greengrass Development Kit CLI](https://github.com/aws-greengrass/aws-greengrass-gdk-cli) produces, but it is written under Nx's own `dist/`, not the component folder GDK expects. With `--gdkConfig`, the generator vends `gdk-config.json` (`build_system: custom`, `custom_build_command` pointing back at this same target) so you can run `gdk component build` or `gdk component publish` directly. The plugin does not read it.

## Deploying and observing locally

:::caution[Run these on the core device]
`<c>-deploy-local` and `<c>-logs` only make sense executed **on** a Greengrass core device (or a container running the [nucleus](https://docs.aws.amazon.com/greengrass/v2/developerguide/greengrass-nucleus-component.html)) — they call `greengrass-cli`, which is installed alongside the nucleus, not on your development machine. Neither target is wired into the project's `dev` target: a routine `nx run <project>:dev` must never mutate a real device as a side effect. Once a deployment reaches the device, follow [Verifying on a real device](#verifying-on-a-real-device).
:::

<NxCommands commands={['run <project>:<component-name>-deploy-local']} />

Creates one local deployment (`greengrass-cli deployment create --recipeDir ... --artifactDir ... --merge <ComponentName>=<version>`), then polls `greengrass-cli component list` until the component settles. It exits 0 once the component holds `RUNNING` (or `FINISHED`) across three checks two seconds apart, and non-zero on `BROKEN` or `ERRORED`, or when the component has not settled within 120 seconds (`GREENGRASS_DEPLOY_TIMEOUT_SECONDS` changes that bound) — printing the state it reached and the last 40 lines of the component's log. Three checks rather than one because the nucleus reports `RUNNING` as soon as it starts the process, so a component that crashes a few seconds in is `RUNNING` at the first check. `FINISHED` passes, for a component deliberately made one-shot, but is called out: a generated component subscribes to IPC and runs until it is stopped, so `FINISHED` usually means it exited immediately. That check exists because a deployment can report success while the component is broken, see <Link path="guides/greengrass-deployment#a-successful-deployment-is-not-a-running-component">A Successful Deployment Is Not a Running Component</Link>.

For a concrete `ComponentVersion`, bump the version before re-deploying. The CLI reports no instance identity, so a re-deploy of a version already on the device can read the outgoing instance's state. The target warns when it sees that case rather than claiming a verdict it cannot support. A `NEXT_*` version resolves to a new version above every version the device already holds, so this warning does not apply.

Local deployments resolve the recipe's `s3://` placeholder artifact from `--artifactDir` by component name and version; this generator is experimental while that flow is being verified across nucleus versions.

<NxCommands commands={['run <project>:<component-name>-logs']} />

Tails the component's log file (`<GREENGRASS_ROOT>/logs/<ComponentName>.log`) in follow mode until you press Ctrl-C.

Both targets read `GREENGRASS_ROOT` from the environment, defaulting to `/greengrass/v2`.

## Verifying on a real device

CI cannot prove on-device behaviour. It proves that `CreateComponentVersion` and `CreateDeployment` succeed, not that the component runs. This section is the procedure the author's receipts followed, in order. Every command here appears in one of those receipts.

1. **The device as the cloud sees it.** Nucleus version, platform and health in one call. `architecture` is `aarch64` here, never `arm64`; that token is what the recipe manifests must carry.

   ```bash
   aws greengrassv2 get-core-device --core-device-thing-name <thing> \
     --query '{status:status,coreVersion:coreVersion,platform:platform,architecture:architecture}'
   ```

2. **Deployment status, then component state.** A deployment and its IoT job can report `SUCCEEDED` while the component is `BROKEN` and the device is `UNHEALTHY`, with no rollback. Read both, and treat only the second as evidence.

   ```bash
   aws greengrassv2 list-effective-deployments --core-device-thing-name <thing>
   aws greengrassv2 list-installed-components --core-device-thing-name <thing>
   ```

   On the device itself, before and after the deployment:

   ```bash
   sudo /greengrass/v2/bin/greengrass-cli component list
   ```

3. **The bytes the device fetched.** One archive per manifest the device matched, and nothing from any other architecture.

   ```bash
   sudo ls /greengrass/v2/packages/artifacts/<ComponentName>/<version>/
   sudo ls /greengrass/v2/packages/artifacts-unarchived/<ComponentName>/<version>/
   sudo find /greengrass/v2/packages -iname "*<other-architecture>*"   # expect no output
   ```

4. **The machine code.** With `ipc: true`, `file` on the vendored `aws-crt` addon must name the device's architecture. The author has not run the TypeScript component through this procedure on hardware yet, so treat this step as the check to perform, not as a claim already made.

   ```bash
   sudo find /greengrass/v2/packages/artifacts-unarchived/<ComponentName>/<version>/ -name "aws-crt-nodejs.node" -exec file {} \;
   ```

5. **Liveness.** Two samples of the component's own log, spaced apart, with no restart between them. With `ipc: true` the first lines also show the IPC connection and a published message.

   <NxCommands commands={['run <project>:<component-name>-logs']} />

   ```text
   INFO:awsiot.eventstreamrpc:<Connection ...> /greengrass/v2/ipc.socket:0> connected
   INFO:<ComponentName>:Published heartbeat 0 to <ComponentName>/heartbeat
   INFO:<ComponentName>:Published heartbeat 8 to <ComponentName>/heartbeat
   ```

6. **The teardown sweep.** After the infrastructure is destroyed, nothing of the component remains in the registry, in the bucket, or on the device.

   ```bash
   aws greengrassv2 list-component-versions --arn arn:aws:greengrass:<region>:<account>:components:<ComponentName>
   aws s3api head-bucket --bucket <artifact-bucket>          # expect a 404
   aws greengrassv2 list-installed-components --core-device-thing-name <thing>
   ```

The deployment guide records the two failure modes this procedure exists for: <Link path="guides/greengrass-deployment#a-successful-deployment-is-not-a-running-component">a successful deployment that is not a running component</Link>, and <Link path="guides/greengrass-deployment#ipc-components-fail-on-a-sudo-rs-device">IPC components that fail on a sudo-rs device</Link>.

## File ownership

The component targets in `project.json` are framework-owned and re-synced to the current definition on every generator run. With `--gdkConfig`, `gdk-config.json` is also framework-owned and re-synced. A run without `--gdkConfig` removes it. The vended scripts under `packages/common/scripts/src/greengrass/` - including `vendor-crt-addon.ts`, vended only when `ipc: true` - are created once and never overwritten, so your patches survive. Delete those files and re-run the generator to pick up their current versions.

Because those scripts never refresh on their own, this generator checks them up front: in a workspace whose Greengrass scripts were vended by a plugin version that predates bundled (TypeScript) components, it refuses to generate and tells you to delete and re-vend them — otherwise the `<c>-artifact` target would fail later with an unexplained `Nothing to package`.

The post-deployment verification described above is not enforced that way: a workspace vended before it keeps a `deploy-local.ts` that only submits the deployment and reports `greengrass-cli`'s own exit status. That still deploys correctly, so refusing to generate over it would be disproportionate — the generator warns instead, naming the file. Take the new check by deleting `packages/common/scripts/src/greengrass/` and re-running the generator (re-apply any patches of your own afterwards).

## Recipe ownership

`recipe.yaml` is written once, with the options you chose at generation time, and never rewritten by a later run of this generator, so re-running it with the same component name leaves your edits alone. Add configuration, lifecycle steps or dependencies directly in the recipe as your component grows.

Two things in the generated recipe are load-bearing and worth understanding before you edit them:

```yaml
Manifests:
  - Artifacts:
      - Uri: s3://BUCKET_NAME/COMPONENT_NAME/COMPONENT_VERSION/<component-name>.zip
        Unarchive: ZIP
    Lifecycle:
      Run: node {artifacts:decompressedPath}/<component-name>/index.js
```

- The `BUCKET_NAME` / `COMPONENT_NAME` / `COMPONENT_VERSION` placeholders are the same ones GDK uses. `<c>-artifact` copies them through to the resolved recipe untouched; a later publishing step substitutes them with the real bucket and key.
- The `Uri` basename must stay `<component-name>.zip`, because that is the name `<c>-artifact` gives the zip, and Greengrass unarchives it to `{artifacts:decompressedPath}/<component-name>/` — which is where the matching `Run` script looks for `index.js`, the bundle's output filename. `<c>-artifact` fails with an explicit message if you break that pairing. This holds even with `platform: linux-amd64-arm64`: a rolldown bundle is pure JavaScript, so it serves both architectures under the same `<component-name>.zip` name, referenced by two manifests instead of one.
- The device must have a **modern `node` binary on `PATH`** — the bundle is pure JavaScript with no ABI pinning (unlike Python's interpreter-version trap), but it still needs Node.js 18 or later to run.

### Automatic versioning (NEXT_PATCH, NEXT_MINOR, NEXT_MAJOR)

Set `ComponentVersion` to one of these sentinels to resolve the version at deploy time.

| Sentinel | Highest published 1.4.2 becomes | Nothing published yet |
| --- | --- | --- |
| `NEXT_PATCH` | `1.4.3` | `1.0.0` |
| `NEXT_MINOR` | `1.5.0` | `1.0.0` |
| `NEXT_MAJOR` | `2.0.0` | `1.0.0` |

The version resolves from the highest version already published in the account and Region. The first publication uses `1.0.0`. Unchanged content re-deploys the same version. The published version carries a content tag, so the plugin does not republish it. Changed content publishes the next number. The plugin never rewrites `recipe.yaml`.

In this mode, the artifact key is `<ComponentName>/<sha256>/<file>`. The deployment must receive the resolved version. Follow the <Link path="guides/greengrass-deployment#automatic-versioning">automatic versioning deployment guidance</Link> when you connect this component to a deployment.

`<c>-deploy-local` resolves the sentinel on the device instead of against the cloud registry. It takes the highest strict version among the installed version and the version directories under `<GREENGRASS_ROOT>/packages/artifacts/<ComponentName>/` and `<GREENGRASS_ROOT>/packages/artifacts-unarchived/<ComponentName>/`, then bumps it. A store that is missing or unreadable is skipped with one log line. With `--gdkConfig`, GDK understands only `NEXT_PATCH`; a `gdk-config.json` file carrying `NEXT_MINOR` or `NEXT_MAJOR` is invalid for GDK. The plugin never invokes GDK.

### Component version immutability

`ComponentVersion` in `recipe.yaml` is user-owned from the start. Once a version of a component is published to AWS IoT Greengrass, that version's content can never change - publishing again under the same version with different content is rejected. Keep a concrete version and bump it by hand whenever you change the component. Or use an automatic versioning sentinel. Two quotas bind that workflow, and neither is adjustable: AWS IoT Greengrass keeps at most 5,000 versions per component per Region, so a bump-per-deploy habit has a ceiling, and `CreateComponentVersion` allows 1 request per second per Region, so a deploy that publishes many components at once is rate-limited. The <Link path="guides/greengrass-deployment#service-quotas-that-bind-generated-code">deployment guide</Link> lists both with their consequences.

<OptionFilter when={{ ipc: true }} description="ipc=true wires a least-privilege accessControl block">

### IPC access control

With `ipc: true`, the recipe includes a least-privilege `accessControl` block scoped to the component's own topic:

```yaml
ComponentConfiguration:
  DefaultConfiguration:
    accessControl:
      aws.greengrass.ipc.pubsub:
        <ComponentName>:pubsub:1:
          policyDescription: Allow publishing heartbeat messages to this component's own topic.
          operations:
            - aws.greengrass#PublishToTopic
          resources:
            - <ComponentName>/heartbeat
```

Depending on `aws-iot-device-sdk-v2` alone does not authorize IPC operations — Greengrass enforces this `accessControl` policy independently, so widen `operations`/`resources` here as your component needs to publish or subscribe to more topics.

On a core device whose `sudo` is `sudo-rs` — the default on Ubuntu 25.10 and later — no IPC component can start at all, whatever this policy allows. See <Link path="guides/greengrass-deployment#ipc-components-fail-on-a-sudo-rs-device">IPC Components Fail on a sudo-rs Device</Link> for the one-line fix on the device.

</OptionFilter>

## Implementing your component

<OptionFilter when={{ ipc: true }} description="ipc=true — main.ts publishes over the Greengrass IPC client">

With `ipc: true`, `main.ts` uses [`aws-iot-device-sdk-v2`](https://github.com/aws/aws-iot-device-sdk-js-v2)'s `greengrasscoreipc` client to publish a heartbeat message to the component's own local topic every 30 seconds:

```ts
import { greengrasscoreipc } from 'aws-iot-device-sdk-v2';

export async function publishHeartbeat(
  client: greengrasscoreipc.Client,
  sequence: number,
): Promise<void> {
  await client.publishToTopic({
    topic: TOPIC,
    publishMessage: { jsonMessage: { message: { sequence } } },
  });
}
```

</OptionFilter>

<OptionFilter when={{ ipc: false }} description="ipc=false — main.ts is a plain long-running loop">

With `ipc: false` (the default), `main.ts` is a plain long-running loop that logs a heartbeat every 30 seconds, with no Greengrass SDK dependency at all - and no on-device install step, since the bundle is fully self-contained.

</OptionFilter>

### Why `ipc` defaults to false here, but true in Python

`ipc: true` is now as self-contained as the Python component - the remaining cost is about 2.3 MB of
native binary in the artifact per targeted architecture, plus an `accessControl` block. The default
stays `false` only so existing invocations keep producing what they produce today.

### The `aws-crt` native addon

<OptionFilter when={{ ipc: true }} description="Only relevant when ipc=true, since aws-iot-device-sdk-v2 depends on aws-crt">

`aws-iot-device-sdk-v2` depends on [`aws-crt`](https://github.com/awslabs/aws-crt-nodejs), whose native addon a bundler cannot inline. `aws-crt` publishes that addon prebuilt for every platform it supports inside the npm package, and the addon is N-API based, so one binary serves every Node.js 18 or later runtime. No compiler is involved anywhere. The `<c>-vendor` target copies your target architecture's copy into a staged tree next to the bundle, which `<c>-artifact` then zips:

```
my-component.zip
|- index.js
`- native/aws-crt/linux-arm64-glibc/aws-crt-nodejs.node
```

and the recipe tells `aws-crt`'s loader where it landed:

```yaml
Lifecycle:
  Setenv:
    AWS_CRT_NODEJS_BINARY_RELATIVE_PATH: native/aws-crt/linux-arm64-glibc/aws-crt-nodejs.node
  Run: node {artifacts:decompressedPath}/<component-name>/index.js
```

There is no install step. The component itself needs a `node` binary and nothing else - no `npm`, no compiler, and no network access of its own, at deployment or at any later nucleus restart. A fresh cloud deployment still downloads the recipe and the artifact through the nucleus, exactly as it does for any component. The decompressed artifact folder stays read-only, which is what AWS documents it as.

The vendored binary needs glibc 2.17 or later. It adds about 2.3 MB to the zip per targeted architecture, and unpacks to 5.4 MB for `linux-arm64-glibc` or 6.9 MB for `linux-x64-glibc`, so `platform: linux-amd64-arm64` pays that cost twice. A musl device (Alpine) is not covered: `aws-crt` ships `dist/bin/linux-<arch>-musl/aws-crt-nodejs.node` in the same npm package, so copy that binary onto the device yourself and point `AWS_CRT_NODEJS_BINARY_ABSOLUTE_PATH` at it.

:::note[Components generated before this change]
Earlier `ipc: true` components carry `Install: cd {artifacts:decompressedPath}/<component-name> && npm install --omit=dev`, which writes `node_modules` into the artifact folder AWS documents as read-only, needs `npm` and the network at every nucleus launch, and loses the installed tree on every version bump. `recipe.yaml` and `rolldown.config.ts` are yours, so no generator run rewrites them. To migrate:

1. Delete `packages/common/scripts/src/greengrass/` and re-run the generator with the same options, then re-apply any patches of your own to those scripts.
2. Delete `external: ['aws-iot-device-sdk-v2'],` from this component's entry in `<project>/rolldown.config.ts`.
3. In `<project>/greengrass/<component-name>/recipe.yaml`, in every manifest, delete the `Install:` line and add the `Setenv` block shown above, using `linux-arm64-glibc` under `architecture: aarch64` and `linux-x64-glibc` under `architecture: amd64`.
4. Delete `<project>/greengrass/<component-name>/package.json`.
5. Bump `ComponentVersion`. The artifact bytes change and published versions are immutable.

On a device that already ran the old recipe, `node_modules` is left inside the old version's unarchived artifact folder, which the nucleus deletes with that version.
:::

</OptionFilter>

## Supported platforms

The `platform` option only affects the recipe manifest's `Platform` block - the bundle itself is pure JavaScript and is not platform-specific. Multi-architecture manifests are supported for `linux-amd64` plus `linux-arm64` via `platform: linux-amd64-arm64`. Windows cores, `linux-any` and any third architecture remain deferred, matching `py#greengrass-component`.

<OptionFilter when={{ platform: 'linux-amd64-arm64' }} description="linux-amd64-arm64 writes two manifests over one bundle">

### Multi-architecture components (`platform: linux-amd64-arm64`)

Because the bundle is pure JavaScript, `platform: linux-amd64-arm64` writes **two manifests over the same one artifact** - unlike the Python component, which builds one zip per architecture:

```yaml
Manifests:
  - Platform:
      os: linux
      architecture: amd64
    Artifacts:
      - Uri: s3://BUCKET_NAME/COMPONENT_NAME/COMPONENT_VERSION/<component-name>.zip
        Unarchive: ZIP
    Lifecycle:
      Run: node {artifacts:decompressedPath}/<component-name>/index.js
  - Platform:
      os: linux
      architecture: aarch64
    Artifacts:
      - Uri: s3://BUCKET_NAME/COMPONENT_NAME/COMPONENT_VERSION/<component-name>.zip
        Unarchive: ZIP
    Lifecycle:
      Run: node {artifacts:decompressedPath}/<component-name>/index.js
```

<OptionFilter when={{ ipc: true }} description="ipc=true adds its own Setenv to every manifest">

With `ipc: true` each manifest carries the same `Setenv` shape shown under [The `aws-crt` native addon](#the-aws-crt-native-addon) above - each manifest's own `Setenv` names only its own architecture's addon, and the single zip holds both.

### Changing `platform` after the first run

`platform` shapes only the **first** generation of `recipe.yaml`, whichever value you pick. A later run with a different `platform` — including a run that simply omits the option, since it defaults to `linux-arm64` — is refused, because `recipe.yaml` is user-owned and never rewritten. The error names the platform to re-run with if you did not mean to change it, and otherwise prints the full `Manifests` block the new platform expects (with the `Setenv` block included when `ipc: true`) to paste in by hand, together with the reminder to bump `ComponentVersion`, since published versions are immutable.

`ipc` shapes only the first generation of `recipe.yaml` too, but a later run that flips it is **not** refused. Turning `ipc` on afterwards adds the `<c>-vendor` target and stages the addon, yet leaves your `recipe.yaml` without the `Setenv` block that points `aws-crt`'s loader at it - the component then fails on the device with `AWS CRT binary not present`. Add that block by hand, following steps 3 and 5 of the migration note under [The `aws-crt` native addon](#the-aws-crt-native-addon).

### Nucleus classic vs nucleus lite

The generated recipe and targets are verified against the [classic nucleus](https://docs.aws.amazon.com/greengrass/v2/developerguide/greengrass-nucleus-component.html) (`aws.greengrass.Nucleus`). [Nucleus lite](https://docs.aws.amazon.com/greengrass/v2/developerguide/greengrass-nucleus-lite-component.html) (`aws.greengrass.NucleusLite`) is a smaller runtime for constrained devices, and it is not equivalent:

- Lite runs generic components only, and supports a subset of the recipe keys classic accepts.
- Lite implements a subset of the IPC operations, so an `accessControl` policy that classic honours may not be enforceable there.
- Lite gained container support only in v2.15 (July 2025).

A component that works on classic can therefore misbehave on lite. Test on the nucleus your fleet actually runs before shipping; there is no runtime capability detection in the generated code.
