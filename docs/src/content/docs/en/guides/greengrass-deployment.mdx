The `greengrass-deployment` generator creates a small TypeScript library for typed [AWS IoT Greengrass v2](https://docs.aws.amazon.com/greengrass/v2/developerguide/what-is-iot-greengrass.html) component wiring, plus (unless `--infra none`) the CDK constructs or Terraform modules an `AWS::GreengrassV2::Deployment` and its artifact bucket need: a retained artifact bucket, and a deployment targeting the thing, thing group, or ARN you target.

Publishing a component's version is handled separately, by escalating a <Link path="guides/py-greengrass-component">`py#greengrass-component`</Link> with `--infra component-version` - this generator only owns the deployment side (the target, the artifact bucket, and the `AWS::GreengrassV2::Deployment` resource itself).

## Usage

Getting a deployment installing components onto real devices takes three steps:

1. **Generate the deployment** - creates the typed component library and (unless `--infra none`) the artifact bucket and `AWS::GreengrassV2::Deployment` infrastructure.
2. **Wire in each component** - a freshly generated deployment's `components` map is empty, so left alone it deploys nothing.
3. **Wire the infrastructure dependency** - orders the deployment after the component versions it references (see [Infrastructure](#infrastructure) below).

At most one of `thingGroupName`, `thingName` or `targetArn` may be set, and it must be the one matching the `target` option:

| `target`       | Option             | Behaviour                                                          |
| -------------- | ------------------ | ------------------------------------------------------------------ |
| `thing-group`  | `thingGroupName`   | Creates a new `AWS::IoT::ThingGroup`, named after the project when omitted |
| `thing`        | `thingName`        | Imports an existing thing by name - required                       |
| `existing-arn` | `targetArn`        | Imports an existing thing or thing group by ARN - required          |

`thingGroupName` names a group this generator creates, so it defaults to the project name. `thingName` and `targetArn` name resources that already exist, so the generator refuses to guess and asks for them.

A literal (non-token) `targetArn` is validated at synth time against the deploying stack's own account and region, so a copy-pasted ARN from the wrong environment fails synth rather than deploying somewhere unexpected.

### 2. Wire in each component

`components.ts` (and `components.json` on Terraform) starts empty, and an empty `components` map deploys nothing - the deployment applies cleanly and installs zero components. For each Greengrass component (<Link path="guides/py-greengrass-component">`py#greengrass-component`</Link> or <Link path="guides/ts-greengrass-component">`ts#greengrass-component`</Link>, generated with `--infra component-version`) you want this deployment to install, run the <Link path="guides/connection/greengrass-deployment-greengrass-component">connection</Link> generator:

<RunGenerator generator="connection" />

Select this deployment as the source project and the component's host project as the target. This adds an entry to `components.ts` (and to `components.json` on Terraform) keyed by the component's `ComponentName`, at the `ComponentVersion` its `recipe.yaml` currently declares - see <Link path="guides/connection/greengrass-deployment-greengrass-component">its guide</Link> for exactly what it writes, and for re-running it after a version bump.

You can also write the entry by hand instead - the connection generator only saves you the typing, and the cross-check between the two files. **On Terraform, editing `components.ts` alone deploys nothing:** `components.json` is the file the `deployment` module reads, so a hand-wired component needs an entry in both (see [Infrastructure](#infrastructure) below for the JSON shape). Add an entry per component you deploy:

```ts title="packages/my-deployment/src/components.ts"
export const components: Record<string, DeploymentComponent> = {
  'com.myscope.MyComponent': { componentVersion: '1.0.0' },
};
```

`configurationUpdate.merge` is a plain object here, not the JSON string `AWS::GreengrassV2::Deployment` expects. Write the configuration as ordinary TypeScript and the vended `GreengrassDeployment` construct serialises it for you:

```ts title="packages/my-deployment/src/components.ts"
export const components: Record<string, DeploymentComponent> = {
  'com.myscope.MyComponent': {
    componentVersion: '1.0.0',
    configurationUpdate: {
      merge: { logLevel: 'DEBUG', sampleIntervalSeconds: 30 },
      reset: ['/legacySetting'],
    },
  },
};
```

The generated app construct accepts a `components` prop, so your infra stack wires the deployment's typed component library straight through:

```ts title="packages/infra/src/stacks/application-stack.ts"
import { MyComponent, MyDeployment } from '@my-scope/common-constructs';
import { components } from '@my-scope/my-deployment';

const deployment = new MyDeployment(this, 'MyDeployment', { components });
const myComponent = new MyComponent(this, 'MyComponent', {
  bucket: deployment.artifactBucket,
});
// Order the deployment after every component version it references:
// CloudFormation creates unrelated resources in parallel, so without this

deployment.dependOn(myComponent);
```

The artifact bucket is a **separate module** from the deployment, not a property on it. A component version's module needs the bucket's name before it can be created, and the deployment must be created only after that component version exists - bundling both in one module the way the CDK construct does would force a dependency cycle the moment your root module wires that ordering with `depends_on`. Wire them together yourself:

```hcl title="packages/infra/src/main.tf"
module "my_deployment_artifact_bucket" {
  source = "../../common/terraform/src/app/greengrass-deployment/my-deployment-artifact-bucket"
}

module "my_component" {
  source      = "../../common/terraform/src/app/greengrass-component/my-component"
  bucket_name = module.my_deployment_artifact_bucket.bucket_name
}

module "my_deployment" {
  source = "../../common/terraform/src/app/greengrass-deployment/my-deployment"

  # Mirrors the CDK construct's `deployment.dependOn(myComponent)`: without
  # this, the IoT job can reach core devices before the version exists in
  # the registry.
  depends_on = [module.my_component]
}
```

The `deployment` module's `components` variable defaults to reading `packages/my-deployment/src/components.json`. **On Terraform that JSON file is what gets deployed - `components.ts` is not read by anything.** Terraform cannot import a TypeScript module, so a Terraform deployment vends both files and the <Link path="guides/connection/greengrass-deployment-greengrass-component">connection</Link> generator writes both; `components.ts` stays as the typed, documented view of the same wiring. Both files are yours to edit, and the connection generator never rewrites an entry either one already holds - it warns instead, on both. If the two ever disagree about a component's version it refuses to run, because Terraform would deploy one version while `components.ts` documents the other. Its keys are snake_case, matching the `awscc_greengrassv2_deployment` schema, unlike `components.ts`'s camelCase:

```json title="packages/my-deployment/src/components.json"
{
  "com.myscope.MyComponent": { "component_version": "1.0.0" }
}
```

Pass `components` explicitly to the module block only to override that file with a value it cannot express (for example, `configuration_update.merge` must be pre-encoded with `jsonencode(...)`).

A literal `target_arn` is cross-checked against the current account, region and partition, the same way the CDK construct's `assertArnMatchesStack` checks it against the deploying stack. One difference in *when* it fires: the check reads `aws_caller_identity`, and the `depends_on` above stops Terraform reading that until the component modules exist, so it is deferred from plan to apply. It still fails before the deployment is created, and with a clearer message than the API's. Independently of it, the awscc provider validates the ARN's shape (`arn:<partition>:iot:<region>:<account>:thing|thinggroup/...`) at plan time.

### Bucket Naming

Left unset, the generated `<name>-artifact-bucket` module names the created bucket `<name>-artifacts-<account-id>-<region>-<random-suffix>` rather than letting AWS generate an opaque `terraform-<random>` name - a bucket created that way carries no workspace or deployment identity, so a human doing manual cleanup (or recovering from a lost state file) has only a creation timestamp and a tag to go on. The random suffix lives in Terraform state, so the name is stable across applies. Pass `bucket_name` on the underlying `core/greengrass/artifact-bucket` module call to set a fixed name instead (S3 bucket names must be globally unique), or `existing_bucket_name` to adopt a bucket this workspace should not own.

A bucket's name cannot be changed in place, so anything that changes the name Terraform computes - editing `bucket_name_prefix`, or upgrading a workspace whose bucket was created before this naming existed - plans a **replacement**. `prevent_destroy` refuses that plan rather than destroying a bucket holding published artifacts, and refuses it plan-wide, so nothing else applies either. Keep the existing bucket by naming it explicitly: set `bucket_name` to the name already in state.

### Retention Diverges From CDK Here

`prevent_destroy = true` is applied to the created artifact bucket only, and that is the one place the CDK constructs' `RemovalPolicy.RETAIN` default carries over. It is deliberately **not** applied to the component version or the deployment, and Terraform has no equivalent of `RemovalPolicy.RETAIN` for them:

- `prevent_destroy` rejects any plan that needs to replace the resource, rather than retaining anything. Both a component version (`inline_recipe`) and a deployment (`components`) are replaced on change, so it would refuse the ordinary "bump `ComponentVersion` in `recipe.yaml`, re-deploy" workflow outright.
- So on Terraform, a replaced component version is **deleted** from the Greengrass registry, along with its artifact object in S3, where the CDK path retains both. The hashed artifact key means every content change is a new object, so nothing is overwritten either way - the difference is only whether the outgoing object is left behind.
- Both resources use `create_before_destroy` instead, which is what keeps the safety property `RETAIN` was there for: the incoming version is published first, so `CreateComponentVersion` rejects a version that reuses an existing `ComponentVersion` with different content, and the outgoing version is deleted only after the deployment has been revised off it.

To keep a published component version that Terraform is about to replace, drop it from state first so Terraform stops managing it and leaves it in AWS:

```bash
terraform state rm 'module.my_component.module.component_version.awscc_greengrassv2_component_version.this'
terraform state rm 'module.my_component.module.component_version.aws_s3_object.artifact'
```

To keep one while deleting its module from the configuration entirely, use a [`removed` block](https://developer.hashicorp.com/terraform/language/resources/syntax#removing-resources) with `lifecycle { destroy = false }`.

The artifact bucket's `prevent_destroy` cannot be overridden per module call the way the CDK prop can - it is a Terraform lifecycle literal. A workspace that genuinely needs to tear the bucket down must remove the `lifecycle` block by hand before `terraform destroy`.

### The awscc Provider

## The Token Exchange Role Grant

Every Greengrass core device assumes a *token exchange role* to reach AWS services, including fetching component artifacts from S3. Pass that role's ARN as `tokenExchangeRoleArn` and the generated construct grants it `s3:GetObject` - and only `s3:GetObject` - on the artifact bucket's objects:

```ts
this.artifactBucket.grantReadTo(
  Role.fromRoleArn(this, 'TokenExchangeRole', tokenExchangeRoleArn, { mutable: true }),
);
```

**The default key scope is every object in the bucket.** This is deliberate, not an oversight: a core device reads whichever component versions get deployed to it, and that set lives in this deployment's own `components` map, which can gain an entry after this grant is created - there is no generation-time input a narrower default could derive a prefix from. Narrow it only when every component this role's device(s) will ever fetch is known to share a prefix (e.g. one Nx workspace's own component namespace, `com.myscope.*`). Pass `tokenExchangeKeyPrefix` alongside `tokenExchangeRoleArn` to do so:

```ts
this.artifactBucket.grantReadTo(
  Role.fromRoleArn(this, 'TokenExchangeRole', tokenExchangeRoleArn, { mutable: true }),
  tokenExchangeKeyPrefix, // e.g. 'com.myscope.*'
);
```

On Terraform, the same two generator options (baked into the generated `<name>-artifact-bucket` module the same way `--targetArn` etc. are) put these arguments on its module block, alongside the `bucket_name_prefix` of [Bucket Naming](#bucket-naming) and the comments the generator writes:

```hcl title="packages/common/terraform/src/app/greengrass-deployment/my-deployment-artifact-bucket/my-deployment-artifact-bucket.tf"
module "artifact_bucket" {
  source                    = "../../../core/greengrass/artifact-bucket"
  token_exchange_role_arn   = "arn:aws:iam::111111111111:role/GreengrassTokenExchangeRole"
  token_exchange_key_prefix = "com.myscope.*"
}
```

`token_exchange_key_prefix` is only emitted when you pass `--tokenExchangeKeyPrefix`; omitted, the underlying `core/greengrass/artifact-bucket` module's own default (`*`) applies.

Both options are baked in **at generation time only**. The generated app construct and app module are created once and then left alone, so re-running the generator with `--tokenExchangeKeyPrefix` does not narrow a deployment that already exists - narrow that one by editing its own generated file, adding the second `grantReadTo` argument on CDK or the `token_exchange_key_prefix` argument on Terraform.

If you omit `tokenExchangeRoleArn`, attach the equivalent policy to your token exchange role by hand:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::<artifact-bucket-name>/*"
}
```

## CloudFormation Semantics Worth Understanding

<OptionFilter when={{ infra: 'deployment' }} description="Only applies when this generator provisions infrastructure">

**Component versions are immutable.** `AWS::GreengrassV2::ComponentVersion`'s `InlineRecipe` is a replacement property - changing it replaces the resource rather than updating it in place. `CreateComponentVersion` itself rejects a resubmission of an already-published version under different content, so a rebuild that forgot to bump `ComponentVersion` fails the deployment rather than corrupting an already-deployed version. The vended construct also uploads each artifact under a content-hashed S3 key (`<ComponentName>/<Version>/<sha256>/<file>`), so a rebuild's upload can never physically overwrite the bytes an already-published version's artifact URI points at. That `<sha256>` is an aggregate over **all** of a version's artifacts once a `py#greengrass-component` targets more than one architecture (`platform: linux-amd64-arm64`), not any single artifact's own hash - so switching an existing, already-published component to multi-architecture without also bumping `ComponentVersion` fails at `CreateComponentVersion` just like any other same-version content change would.

**A long `ComponentName` can exceed the artifact key limit before it exceeds the service's own limit.** `CreateComponentVersion` accepts a `ComponentName` up to 128 characters, but the vended construct's artifact key (`<ComponentName>/<ComponentVersion>/<sha256>/<file>`) always carries a fixed 64-character content hash plus three `/` separators, and CDK's `BucketDeployment` refuses to synthesize once that key prefix passes 102 characters - so `ComponentName` and `ComponentVersion` combined must stay at or under 35 characters (about 30 characters of `ComponentName` alongside a typical 5-character version like `1.0.0`). The construct fails synth with an actionable message naming both fields, the resulting prefix length, and the limit, rather than surfacing CDK's own generic (and, at the time of writing, off-by-two) `BucketDeployment` tag-key error. Terraform's equivalent module has no such ceiling - it uploads with a plain `aws_s3_object`, bound only by S3's own 1024-byte key limit, which a 128-character `ComponentName` cannot approach.

**Both `DeletionPolicy` and `UpdateReplacePolicy` default to `Retain`** on the component version, the artifact bucket, and the deployment resource. Retained component versions accumulate over time - AWS IoT Greengrass has no automatic cleanup, and it allows [5,000 versions per component per Region](https://docs.aws.amazon.com/general/latest/gr/greengrassv2.html), which is therefore the hard ceiling on how many times you can ever bump one component's version in one Region. Plan a periodic inventory (`ListComponentVersions`) and manual deletion of versions you no longer deploy. On Terraform only the artifact bucket is retained, and a replaced component version is deleted instead - see [Retention Diverges From CDK Here](#retention-diverges-from-cdk-here) for why, and for how to keep one.

**Deployment revisions are replacement updates.** Changing a deployment's `components` or `configurationUpdate` replaces the `AWS::GreengrassV2::Deployment` resource - CloudFormation creates the new revision, and the retained old resource is superseded on the target. [Express mode disables rollback by default](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/stack-failure-options.html#express-mode-and-rollback), and **disabling rollback is not supported for replacement updates**, so an express revision deploy fails with `Replacement type updates not supported on stack with disable-rollback`. The `deploy-sandbox` target always uses express mode, and `deploy` uses it too unless you generated the infra project with `stageConfig`. Pass `--no-express` to deploy a revision through either target. `deploy-ci` never uses express mode, so a pipeline deploys revisions unchanged.

If an express deploy already left the stack in `UPDATE_FAILED`, you have two recovery options. Run `cdk rollback` from the infra project to return the stack to its last stable state. Or re-deploy the last good template with `--express` still set, because CloudFormation requires an update to a failed stack to keep rollback disabled. Then deploy the revision with `--no-express`.

The same applies to the artifact bucket: no S3 lifecycle rule is applied by default, because a published component version's artifact must stay retrievable for as long as any deployment can reference it - a lifecycle rule that expires objects would break existing versions when a new core device joins and fetches them. The bucket is tagged `greengrass-artifact-repository=true` so an inventory pass can find it. When you retire component versions (delete the version, confirm no deployment references it), delete their `<ComponentName>/<version>/` prefixes in the same pass - that is the deliberate, documented cleanup policy this construct expects instead of an automatic rule.

**Deleting a deployment resource removes management state, not running components.** `AWS::GreengrassV2::Deployment` tracks what CloudFormation *intends* to have deployed; deleting it does not uninstall anything already running on target devices. To remove components from devices, deploy an explicit revision that drops them - deleting the CloudFormation resource is not that revision.

**CloudFormation allows at most 10 deployment resources added or deleted per operation.** Batch deployment changes across stacks if you approach that limit.

</OptionFilter>

## Service Quotas That Bind Generated Code

Most [AWS IoT Greengrass quotas](https://docs.aws.amazon.com/general/latest/gr/greengrassv2.html) are far away from anything this generator produces. Three are close enough to plan around. Only one of them is caught before a deployment, and only on CDK - the rest fail at deploy time rather than at synth or plan time.

**The whole recipe crosses the API as one document, capped at 16 KB.** The CDK construct publishes it as `InlineRecipe` and the Terraform module as `inline_recipe`, so the recipe's total serialised size is what counts, not any one field. A generated single-manifest recipe is around 1 KB, so there is real headroom, but two things consume it: a large `ComponentConfiguration.DefaultConfiguration` block, which is yours to author and which nothing here bounds, and one manifest per architecture when you use `platform: linux-amd64-arm64`. Exceeding it fails the deployment with `ValidationException: Invalid Input: Size of the recipe size can't exceed 16KB`. Note that the Service Quotas API currently reports this limit as 8 KB; 16 KB is the value the service actually enforces.

The CDK construct measures the serialised recipe at synth time and fails there instead, naming the recipe, its actual byte size, the 16384 byte limit and how far over it is. It is not a substitute for the deploy-time rejection, because at synth the artifact bucket's name is usually still an unresolved CDK token standing in for a name of 3 to 63 characters: the real name makes the submitted document up to about 88 bytes longer on a two-manifest recipe, and could in principle make it shorter. So the guard compares against the shortest name the token can resolve to, and rejects only a recipe that is too large whatever the bucket ends up being called - a recipe within roughly 100 bytes either side of the cap is still settled at deploy time. The Terraform module has no equivalent check, deliberately: the recipe string embeds the bucket name, which is unknown until apply on a fresh workspace, so a plan-time precondition would be deferred to the same apply in which `CreateComponentVersion` already rejects the recipe. Terraform also has no byte-length function, so the check could not be exact.

**The deployment document is capped at 31 KB for a thing group and 7 KB for a single thing.** Every component's `configurationUpdate` is serialised into that one document, along with the deployment policies and payload overhead, so the budget is shared across all components in the deployment rather than per component. 7 KB for a `--target thing` deployment is tighter than it looks. Greengrass offers large-configuration support that raises the ceiling to 6 MB, but the vended constructs do not enable it, so treat 31 KB and 7 KB as the operative numbers.

**`CreateComponentVersion` is limited to 1 request per second per Region**, against 30 per second for other control-plane operations. Nothing in the vended constructs serialises component-version creation, so a stack publishing several new component versions at once leaves CloudFormation free to create them concurrently. We have not observed throttling - the receipts behind this guide only ever published one or two versions per deploy - so treat this as a caveat to be aware of, not a known failure. If you hit it, split the components across stacks or deploy them in stages.

## Local Deployments Conflict with Cloud Deployments

A local deployment made on the device with `greengrass-cli` - what the component generators' `<c>-deploy-local` target creates - **pins that component to an exact version on that device**, and the nucleus treats the pin as a requirement it must keep satisfying. A cloud deployment asking the same device for a different version cannot satisfy both, so the nucleus refuses the whole deployment rather than choosing:

```
FAILED_NO_STATE_CHANGE ... Component com.myscope.MyComponent version constraints:
LOCAL_DEPLOYMENT requires =1.0.0, thinggroup/my-things requires =1.0.1
```

The version in `components.ts` is not wrong here - the local pin is simply older, and it wins by existing. Remove it on the device, then deploy from the cloud again:

```bash
greengrass-cli deployment create --remove com.myscope.MyComponent
```

This is why local iteration and a deployed fleet do not mix on one device: use `<c>-deploy-local` on a development device, and let the cloud deployment own the devices in your thing group. If you do both on one device, clear the local deployment before every cloud deploy.
