The `greengrass#component` generator produces software for a physical or virtual core device
managed by the AWS IoT Greengrass nucleus. Unit tests, snapshots, and a successful
CloudFormation deployment cannot observe every part of that software's correctness.

## The five validation tiers

| Tier | Proves | Cannot prove |
| --- | --- | --- |
| Unit tests / snapshots | Generated file content, option handling, idempotency, target wiring | That any of it is accepted by AWS or runnable |
| Linked-workspace build | A freshly generated workspace builds out of the box, artifacts are well-formed | That the recipe is valid to the service |
| E2E smoke (upstream CI) | Generate + build across the option matrix, no crashes | Anything requiring AWS credentials or a device |
| Real cloud deploy | `CreateComponentVersion` / `CreateDeployment` accept the output; artifact fetch and IAM grants work | That the component process starts or stays up |
| **Real core device** | The nucleus selects the right manifest, the artifact unpacks, the interpreter and native extensions load, the process runs, IPC connects | - |

Each tier catches defects that the tiers above it cannot see. Keep all five tiers.
Do not run all five tiers in upstream CI.

## Defects that only the device tier found

These defects passed unit tests, built cleanly, and in most cases deployed successfully.

1. **`architecture: arm64` is silently wrong.** The nucleus matches `aarch64`.
   A Docker-style `arm64` produces `LOCAL_RECIPE_NOT_FOUND` on the device.
   Nothing upstream of the device rejects it.
2. **A bare `python3` in the recipe's `Run` resolves to the device's default interpreter**,
   not the one the wheels were vendored for. It gives
   `ImportError: undefined symbol: Py_GetConstant`.
   The recipe now pins `python<requires-python floor>`.
3. **`Source.asset` must target the artifact directory, not the archive with `extract: false`.**
   The latter publishes under the CDK asset's own hashed filename, which no recipe URI can
   reference.
4. **A build-time timestamp in the zip churned the artifact sha256 on every rebuild**,
   so CloudFormation tried to replace an immutable component version and hit
   `AlreadyExists`. DOS-epoch timestamps and sorted entries fix this.
5. **A missing `ComponentVersion` -> `Deployment` dependency edge** let the IoT job reach
   devices before the version existed.
6. **Greengrass nucleus 2.18.3 cannot run IPC components on Ubuntu 25.10+.**
   This was invisible to every other tier.
7. **A deployment can report `SUCCEEDED` while the component is `BROKEN`.**

## A Successful Deployment Is Not a Running Component

A deployment and its IoT job can both report `SUCCEEDED` while the component on the device is
`BROKEN`. Observed on real hardware: the nucleus logged the component `BROKEN` at
04:47:50.169Z and wrote `DeploymentStatus=SUCCEEDED` 14 seconds later, at 04:48:04.732Z:

```text
DeploymentStatusKeeper: Stored deployment status. {DeploymentStatus=SUCCEEDED}
IotJobsHelper: ... {Status=SUCCEEDED, StatusDetails={detailed-deployment-status=SUCCESSFUL}}
```

The IoT job reported `SUCCEEDED` too, and no rollback happened despite
`failureHandlingPolicy: ROLLBACK` in the deployment document. `get-core-device` reported the
device `UNHEALTHY` throughout.

So a green deployment means the device accepted and applied the document, not that anything
it installed runs. Two things are evidence:

```bash
# UNHEALTHY means at least one component on the device is not running
aws --profile <profile> --region <region> greengrassv2 get-core-device \
  --core-device-thing-name <thing-name> --query status

# the component's own lifecycle state: RUNNING, FINISHED, BROKEN, ERRORED, ...
aws --profile <profile> --region <region> greengrassv2 list-installed-components \
  --core-device-thing-name <thing-name>
```

Check both after every cloud deployment, and treat a CloudFormation stack that reaches
`UPDATE_COMPLETE` or a completed Terraform apply the same way: it reports that the deployment
resource was created, nothing about the device. On a development device the
`<component>-deploy-local` target does this check for you: it polls the component's lifecycle
state after submitting the local deployment, prints the tail of the component's log, and
exits non-zero unless the component holds `RUNNING` or `FINISHED` across three checks. Three,
because the nucleus reports `RUNNING` as soon as it starts the process; a single sample also
passes for a component that is about to crash.

## IPC Components Fail on a sudo-rs Device

This is a distribution-versus-nucleus incompatibility, not a defect in the generated
component. Ubuntu 25.10 and later ship [sudo-rs](https://github.com/trifectatechfoundation/sudo-rs)
as the default `sudo`. Greengrass nucleus 2.18.3 launches every component through `sudo -E`
to pass `AWS_GG_NUCLEUS_DOMAIN_SOCKET_FILEPATH_FOR_COMPONENT` and `SVCUID` into the
component's environment. `sudo-rs` accepts `-E`, prints
`sudo: preserving the entire environment is not supported, '-E' is ignored`, and then
discards the environment. The two variables never arrive, so **every** IPC-using component on
that device starts, imports its architecture-specific native extension successfully, and dies:

```text
stderr. sudo: preserving the entire environment is not supported, '-E' is ignored
KeyError: 'AWS_GG_NUCLEUS_DOMAIN_SOCKET_FILEPATH_FOR_COMPONENT'
```

The nucleus restarts it three times and then marks it `BROKEN`. The nucleus uses this
invocation shape, reproduced here with the two `sudo` binaries Ubuntu ships:

```bash
$ sudo env FOO=abc sudo    -n -E -H -u ggc_user -g ggc_group sh -c 'echo [$FOO]'
sudo: preserving the entire environment is not supported, '-E' is ignored
[]
$ sudo env FOO=abc sudo.ws -n -E -H -u ggc_user -g ggc_group sh -c 'echo [$FOO]'
[abc]
```

`ipc` defaults to **true** for a Python `greengrass#component`, so the default generated
Python component is exactly this case.

Classic `sudo` is already installed on Ubuntu: the `sudo` package provides `/usr/bin/sudo.ws`,
and `sudo-rs` provides the `/usr/bin/sudo` alternative that is selected by default. Select the
classic binary and restart the nucleus on the device:

```bash
sudo update-alternatives --set sudo /usr/bin/sudo.ws
sudo systemctl restart greengrass
```

A recipe cannot change how the nucleus launches a component, because the nucleus builds the
`sudo` command line. A privileged `Install` step can switch the device back to classic `sudo`
before the `Run` step, fleet-wide and without the restart: see
<Link path="guides/greengrass-out-of-scope#scenario-switch-a-sudo-rs-fleet-back-to-classic-sudo-from-the-recipe">Beyond the generators</Link>.
`<component>-deploy-local` recognises the signature in the component's log and prints the two
commands above when it sees it. The <Link path="get_started/tutorials/greengrass/2">tutorial's setup script</Link>
selects `sudo.ws` on its Ubuntu 26.04 instance before it installs the nucleus.

## Multi-architecture results

`platform: linux-amd64-arm64` vendors dependencies per architecture and writes one recipe
manifest each. One component version can serve a mixed fleet. Two real devices proved:

- One component version, `com.gg-validate.MultiArch` 1.0.0, exactly one in the registry,
  two platforms on it, both artifacts under one aggregate-sha256 prefix.
- The **aarch64** device (Amazon Linux 2023, Graviton) fetched only
  `multiarch-aarch64.zip` and ran `_awscrt.abi3.so` reporting `ARM aarch64`
  (BuildID `5dfa1679`).
- The **x86_64** device (Ubuntu 26.04) fetched only `multiarch-amd64.zip` and ran the
  same file reporting `x86-64` (BuildID `68c84233`).
- Store-wide negative checks confirmed neither device held a single byte of the other's
  archive.
- Both connected over the nucleus IPC socket and published heartbeats one second apart.

**Manifest selection is active platform matching, not first-match.** The nucleus-persisted
recipe is byte-identical on both devices
(sha256 `7a10ba434a947b2f66bc433ad227020fd5351817442afb51b9d348b4fa92eb04`).
The **amd64 manifest is first** in both. The aarch64 device resolved to the *second*
entry. One device cannot establish that distinction.

This result has two limits:

- The x86 device is Ubuntu and the aarch64 device is Amazon Linux 2023. OS and
  architecture varied together, so the run cannot separate their effects.
- The TypeScript `greengrass#component` adapter accepts the same option and was not
  exercised. Its multi-architecture path remains unit-tested only.

These results were recorded against the previous generator surface. They prove the packaging
and recipe behaviour the current generator reuses, not the current generator itself.

## Verifying on a real device

CI proves that `CreateComponentVersion` and `CreateDeployment` succeed, not that the component
runs. This is the procedure the receipts behind this guide followed, in order.

1. **The device as the cloud sees it.** Nucleus version, platform and health in one call.
   `architecture` is `aarch64` on 64-bit ARM and `amd64` on x86_64; those tokens are what the
   recipe manifests must carry.

   ```bash
   aws --profile <profile> --region <region> greengrassv2 get-core-device \
     --core-device-thing-name <thing-name> \
     --query '{status:status,coreVersion:coreVersion,platform:platform,architecture:architecture}'
   ```

2. **Deployment status, then component state.** A deployment and its IoT job can report
   `SUCCEEDED` while the component is `BROKEN` and the device is `UNHEALTHY`, with no rollback.
   Read both, and treat only the second as evidence.

   ```bash
   aws --profile <profile> --region <region> greengrassv2 list-effective-deployments \
     --core-device-thing-name <thing-name>
   aws --profile <profile> --region <region> greengrassv2 list-installed-components \
     --core-device-thing-name <thing-name>
   ```

   On a device that has the Greengrass CLI component, before and after the deployment:

   ```bash
   sudo /greengrass/v2/bin/greengrass-cli component list
   ```

3. **The bytes the device fetched.** One archive per manifest the device matched, and nothing
   from any other architecture.

   ```bash
   sudo ls /greengrass/v2/packages/artifacts/<ComponentName>/<version>/
   sudo ls /greengrass/v2/packages/artifacts-unarchived/<ComponentName>/<version>/
   sudo find /greengrass/v2/packages -iname "*<other-architecture>*"   # expect no output
   ```

4. **The machine code and the interpreter.** `file` on one vendored native extension must name
   the device's architecture, and the nucleus log's `shell-runner-start` line must show the
   pinned interpreter the wheels were vendored for.

   ```bash
   # Python: the awscrt extension
   sudo file /greengrass/v2/packages/artifacts-unarchived/<ComponentName>/<version>/<component>/_awscrt.abi3.so
   # TypeScript with ipc: true: the aws-crt Node addon
   sudo find /greengrass/v2/packages/artifacts-unarchived/<ComponentName>/<version>/ -name "aws-crt-nodejs.node" -exec file {} \;
   sudo grep -m1 shell-runner-start /greengrass/v2/logs/greengrass.log
   # ... command=["python3.14 .../<component>/main.py"]
   ```

5. **Liveness.** Two samples of the component's own log, spaced apart, with no restart between
   them. With `ipc: true` the first lines also show the IPC connection and a published message.

   <NxCommands commands={['run <project>:<component>-logs']} />

   ```text
   INFO:awsiot.eventstreamrpc:<Connection ...> /greengrass/v2/ipc.socket:0> connected
   INFO:<ComponentName>:Published heartbeat 0 to <ComponentName>/heartbeat
   INFO:<ComponentName>:Published heartbeat 8 to <ComponentName>/heartbeat
   ```

   Without the Greengrass CLI on the device, read `/greengrass/v2/logs/<ComponentName>.log`
   over SSH or Systems Manager, as the <Link path="get_started/tutorials/greengrass/3">tutorial</Link> does.

6. **The teardown sweep.** After the infrastructure is destroyed and the retained resources
   are deleted, nothing of the component remains in the registry, in the bucket, or on the
   device.

   ```bash
   aws --profile <profile> --region <region> greengrassv2 list-component-versions \
     --arn arn:aws:greengrass:<region>:<account>:components:<ComponentName>
   aws --profile <profile> --region <region> s3api head-bucket --bucket <artifact-bucket>   # expect a 404
   aws --profile <profile> --region <region> greengrassv2 list-installed-components \
     --core-device-thing-name <thing-name>
   ```

## Why this does not run in the upstream e2e suite

The upstream `cdk-deploy` e2e jobs assume `DEPLOY_INTEG_TESTS_ROLE_ARN` and deploy into
the maintainers' integration account on every change. Greengrass device assertions do
not belong in that suite for six independent reasons:

1. **Component versions are immutable and retained.** `RemovalPolicy.RETAIN` sits on
   both `DeletionPolicy` and `UpdateReplacePolicy` by design. Every run would leave
   component versions that teardown cannot remove. Greengrass allows 5,000 versions per
   component per Region with no automatic cleanup. The retention policy actively fights
   the teardown the e2e suite needs.
2. **It requires physical or virtual core devices.** The claims that matter are manifest
   selection, interpreter resolution, native extension loading, IPC connection, and
   process liveness. Only a running nucleus can expose them. Provisioning a device per
   run means an EC2 instance, a thing, a certificate, a token exchange role, and a thing
   group per run. All are stateful and slow.
3. **A green deployment is not a green component.** A device-less API assertion would
   produce false confidence.
4. **Cost and wall-clock.** The two validation devices are a `t4g.2xlarge` and a
   `t2.large` running continuously. A single deploy-and-verify cycle takes minutes.
   Per-architecture wheel vendoring makes the build slow. The option matrix multiplies
   both costs on every push.
5. **Hard service ceilings turn the matrix into a cliff.** CloudFormation permits at
   most 10 deployment resources added or deleted per operation. `CreateComponentVersion`
   is limited to 1 request per second per Region. A matrix that fans out hits both.
6. **Platform coverage is the point.** The `sudo-rs` finding exists only because a device
   ran a specific Ubuntu release. A CI runner image proves nothing about the
   distributions users deploy to.

## What each tier owns

- **Upstream CI, every change:** unit tests, snapshots, and the existing
  generate-and-build e2e smoke matrix, including the `greengrass-tutorial` lane that runs
  the tutorial's commands, edits, build and synth. This tier owns option handling,
  idempotency, and file content. It is fast and hermetic. Do not add Greengrass assertions
  to `deploy-invocations.ts`.
- **Manual or nightly, owned by the contributor:** cloud publish and deploy, plus
  on-device verification. The Greengrass Test Framework (GTF) is the eventual home for
  automating this tier. It is deliberately out of initial scope.
- **Graduation criterion for dropping `experimental`:** repeat the validation against
  shipped code, complete one full release cycle with no schema or layout changes, and
  keep the e2e suites stable.

The deployment composition itself is described in the
<Link path="guides/greengrass-component#deploying">Greengrass component guide</Link>, and the
<Link path="get_started/tutorials/greengrass/overview">tutorial</Link> provisions one disposable
EC2 core device to run this procedure against.
